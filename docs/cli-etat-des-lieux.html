La CLI TidyJS rend le même texte que VS Code, est commitée sur une branche de POC, et le chemin rapide traite un fichier Yeap en 0,13 s.

Ce document fait l'état des lieux de la session « CLI exploration » du 6 octobre 2026 (de 19 h 32 à 23 h 41), complété par le travail du 7 octobre : alignement des versions sur Yeap-UI-Apps, réduction du démarrage à froid et repli à deux étages. Il s'appuie sur le transcript de la session, sur plans/cli.md, sur le code du commit d855937 et sur des contrôles relancés le 7 octobre 2026. Chaque chiffre indique sa provenance : revérifié le 7 octobre, mesuré le 7 octobre après intégration et repris de plans/cli.md, ou mesuré pendant la session et repris de son transcript.

Tout le travail tient dans un commit, d855937 (« run TidyJS outside VS Code with editor-identical results »), sur la branche poc/headless-tidy partie de main (d90321e). La branche est poussée sur origin (yeapAi/tidyjs), sans pull request. Le commit supprime src/utils/config.ts, configLoader.ts et diagnostics-cache.ts, et ajoute src/core/, src/cli/, src/vscode/ et test/compat/.

La section 01 décrit ce qui existe, la 02 ce qu'il faut pour formater, la 03 le trajet d'un fichier. La 04 donne les preuves, la 05 le bilan des pistes gardées ou refusées, et la 06 ce qu'on peut encore tenter et ce qui reste à décider.

01

Le moteur est sorti de VS Code, et deux adapters l'utilisent.

La session est partie d'un cahier des charges collé en début de session : pas de simple wrapper, un core sans dépendance à VS Code, un adapter VS Code et un adapter CLI qui fournissent les mêmes abstractions, dont des diagnostics normalisés. Un premier POC avait existé sur une branche feat/cli-poc. La branche n'existe plus et son code est perdu. Il n'en reste que plans/cli-poc.md, dont les découvertes ont été réutilisées.

Le découpage est en place. Dans eslint.config.mjs, une règle no-restricted-imports interdit d'importer vscode en dehors de src/extension.ts et de src/vscode/. Le provider de l'extension et le mode dossier passent par le même pipeline, formatSource dans src/core/pipeline.ts, avec deux profils : editor (format à l'enregistrement) et folder (Format Folder).

Le moteur de formatage n'a pas changé : parser.ts, l'IR et formatter.ts (5 lignes modifiées, pour sortir les notifications). Seuls les entrées (config, diagnostics, chemins) et les sorties (log, notifications) ont été déplacées.

02

Formater ne demande que Node et oxc-parser ; supprimer des imports demande le projet entier.

TidyJS a deux besoins distincts. Trier, grouper et aligner est purement syntaxique : le fichier et sa configuration suffisent. Supprimer des imports (removeUnusedImports, removeMissingModules) exige de savoir ce que TypeScript et ESLint diraient du fichier. Dans VS Code, ces réponses viennent des diagnostics déjà publiés par l'éditeur. La CLI doit les calculer elle-même. Les deux options valent false par défaut, dans src/core/config.ts comme dans le package.json.

Le bundle dist/cli-main.js (ESM, avec shebang), chargé par le lanceur dist/cli.js, embarque oxc-parser (son binaire natif est copié dans dist/), jsonc-parser, tinyglobby, diff et @typescript-eslint/scope-manager. @typescript-eslint/typescript-estree n'y est plus : l'oracle travaille sur l'AST d'oxc-parser. Deux paquets restent externes et sont résolus depuis le projet à l'exécution : typescript et eslint.

03

Un oracle tranche la plupart des fichiers ; les cas douteux passent par TypeScript sur le fichier seul, puis par le programme complet.

La CLI résout d'abord la config du fichier avec le code de l'extension. Ensuite, si une suppression est active et que le fichier a des imports, elle cherche quels imports sont inutilisés ou introuvables. Le core reçoit des TidyDiagnostic et ne sait pas d'où ils viennent. Depuis la correction faite pendant la session, un diagnostic n'est retenu que s'il pointe dans la déclaration d'import qui lie le nom.

L'oracle (src/cli/import-oracle.ts) compte les références de chaque import avec @typescript-eslint/scope-manager, l'analyse de portée d'ESLint, appliquée à l'AST d'oxc-parser. Il résout chaque module avec ts.resolveModuleName et les declare module ambiants du projet. Un import sans référence reçoit un 6133 synthétique, placé sur l'import. Comme VS Code retire tout nom signalé par TypeScript ou par ESLint, ESLint n'a alors pas besoin de tourner.

Le fichier passe en analyse du fichier seul quand tous ses modules se résolvent et qu'un des critères suivants est vrai :

  • fichier .d.ts ;
  • directive @ts-check ou @ts-nocheck ;
  • option noCheck, ou JS avec checkJs: false ;
  • suggestions TypeScript désactivées sans noUnusedLocals ;
  • nom cité dans {@link} (en .ts) ou dans des accolades JSDoc (en .js) ;
  • fabrique JSX en mode classique, ou import réassigné ;
  • import à plusieurs liaisons, toutes inutilisées (TypeScript émet alors un 6192 sans nom).

TypeScript vérifie alors un service qui ne contient que ce fichier (noResolve, noLib, types: [], les autres options du projet), et l'ESLint du projet le lint en parallèle. Avec seulement removeMissingModules, rien ne tourne : aucun module ne manque.

Le fichier passe en analyse complète si un module ne se résout pas, si le fichier ne se parse pas, ou si emitDecoratorMetadata est actif et que le fichier contient des décorateurs. Ces critères ont été mesurés sur TypeScript 5.9 et 6.0.

Le chemin rapide ne s'active que si TypeScript et ESLint sont tous deux autorisés. Avec --no-eslint ou --no-fast-analysis, la condition this.fastAnalysis && this.typescript && this.eslint de src/cli/diagnostics.ts est fausse et l'analyse TypeScript est toujours complète. Pour un projet en TypeScript 7, ni l'oracle ni l'analyse du fichier seul ne s'appliquent, faute d'API JavaScript classique : tout passe par l'API native. --no-diagnostics ou --profile folder sautent tout le calcul.

04

Le démarrage à froid a été réduit le 7 octobre, sans changer le résultat : typescript-estree et sa seconde copie de TypeScript ne sont plus chargés (environ 110 ms), le cache de compilation V8 du lanceur retire 70 à 100 ms par lancement, le cache disque des tsconfig fait passer leur lecture de 34,7 ms à 1,4 ms, le test d'appartenance d'un fichier à un tsconfig n'est plus quadratique, et le transfert brut d'oxc-parser fait passer le parse des 1 976 fichiers de 508 ms à 195 ms. 05

Les outils plus rapides ont été mesurés, et aucun ne reproduit seul la règle de VS Code.

La règle à reproduire est l'union lue par l'extension : un nom est retiré si TypeScript (6133, 6196) ou la règle @typescript-eslint/no-unused-vars le signale, et un module est retiré si TypeScript émet un 2307 ou un 2318. Tout outil qui n'applique qu'une seule de ces deux règles, ou une approximation, rompt la parité. Cliquer une ligne pour en voir le détail.

pisteverdict

  • Option A de la comparaison A/B/C (docs/cli-architecture.md, §2). Ce sont les mêmes moteurs que ceux de l'éditeur. La CLI choisit le projet comme tsserver : tsconfig ou jsconfig, références, ancêtres, sinon projet inféré. Côté ESLint, elle reprend l'algorithme de l'extension ESLint, relu dans son code minifié : workingDirectories, !cwd, customizations, quiet, validate, probe, nodePath. Avec ESLint 9, ruleFilter limite l'exécution aux règles utiles.

  • Démarrage d'Electron, xvfb sous Linux, attente des diagnostics : trop lourd et instable pour une CLI. VS Code n'est gardé que comme banc d'enregistrement des sorties de référence (npm run test:compat:record). L'option C, hybride, a été écartée pour la même raison.

  • C'est le défaut actuel ; --no-fast-analysis le désactive. Il fait passer un fichier de 2,3 s à 0,13 s sur Yeap, sans écart observé. Depuis le 7 octobre, il travaille sur l'AST d'oxc-parser : sur les 1 976 fichiers de Yeap, liaisons, références, écritures, positions, présence de JSX et mots JSDoc sont identiques à ceux de typescript-estree. Ses limites, reconnues en fin de session : environ 300 lignes de règles maison qui doivent suivre TypeScript et typescript-eslint, une hypothèse (une référence pour ESLint en est une pour TypeScript) vérifiée sur Yeap mais pas démontrée, des modules ambiants recensés en partie seulement (dans ce cas, il se replie), et aucun effet pour les projets en TS 7.

  • Aucune ne change le résultat. ESLint tourne dans un processus, pas dans un thread, pour garder process.chdir possible. Son processus ne démarre qu'au premier fichier qui en a besoin, sauf avec --no-fast-analysis, où il est préchauffé dès le lancement.

  • FILES_PER_WORKER = 400 et MAX_AUTOMATIC_WORKERS = 2 dans src/cli/parallel.ts. Au-delà de deux workers en TS 6, chaque worker revérifie les déclarations partagées : sur 1 124 fichiers, quatre workers consommaient 2,4 fois le CPU pour un gain moindre. Cette option a été écartée.

  • Option 4 de la session : ne traiter que les fichiers modifiés depuis HEAD (plus les non suivis), ou les fichiers indexés. Le coût fixe de chargement reste, mais il n'est payé qu'une fois.

  • Utilisé automatiquement si le projet est en TS 7, sinon avec --typescript <dossier>. En analyse complète, il divise le temps par trois environ. Les résultats sont identiques sur les bancs Yeap, mais rien ne le garantit : TS 7 a supprimé baseUrl (TS5102) et refuse les paths non relatifs (TS5090), ce que la session a constaté sur le tsconfig de TidyJS lui-même. Un projet qui en dépend verrait des modules « introuvables » que TS 6 trouve. VS Code n'a jamais tourné en TS 7 dans les tests. Pendant l'essai, l'installation de TS 7 sous alias avait remplacé le binaire tsc de node_modules/.bin. L'alias a été retiré, et TS 7 vit désormais dans .vscode-test/ts7 (npm run test:ts7:setup).

  • Rien à gagner sur Yeap, qui n'active pas le linting typé. Ailleurs, un parse non typé ne fait pas échouer les fichiers hors projet, alors que le parse typé de l'éditeur échoue sur ces fichiers et ne signale alors aucun nom inutilisé. Le résultat pourrait donc différer.

  • Ce n'est pas exact : ESLint signale des noms que TypeScript juge utilisés ({@link}, @ts-nocheck, jsxPragma différent). Seule la forme exacte a été gardée, à travers l'oracle.

  • Diagnostics identiques sur 96 fichiers, mais le programme chargeait encore 3 087 fichiers sur 3 226 à cause des imports denses de l'application. On gagne 1,5 s contre 2,0 s, ce qui ne vaut pas le risque.

  • Il vérifie tout apps/paye en 2,2 s, même pour un seul fichier. Avec --noUnusedLocals --noUnusedParameters, il trouve les mêmes diagnostics que TS 6. Il a été refusé pour plusieurs raisons : il ne donne que les erreurs de tsc, donc pas les suggestions que lit VS Code (JS sans checkJs, fichiers hors tsconfig) ; sa sortie est du texte, pas une API ; il n'existe qu'en canary ; il applique les règles de TS 7. Il a été testé avec une copie téléchargée dans le scratchpad de la session.

  • Tout Yeap (1 962 fichiers) passe en 0,26 s, contre 7,5 s pour ESLint, et 1 ou 20 fichiers en 0,06 s. Ses décisions sur les imports inutilisés sont identiques à celles de VS Code sur les 1 962 fichiers. Sur 15 cas limites, il diffère une fois : import React avec jsx: react-jsx, que TypeScript juge inutilisé et qu'ESLint garde. Il ne remplace donc que la partie ESLint. Il ne lit pas la config ESLint : il faut lui recopier les options de no-unused-vars (^_ chez Yeap). Gain estimé, non mesuré : environ 0,3 s par lancement.

  • Sur 20 fichiers Yeap, il trouve les 20 inutilisés et les 10 modules manquants injectés (20 no-unused-vars, 10 TS2307). Il traite 1 fichier en 0,7 à 1,0 s et 20 fichiers en 1,4 s. Il ne garantit pas la parité : il tourne en TS 7, il ne remonte que les erreurs (pas les suggestions, donc le cas React disparaît) et il ignore la config ESLint. Il cherche tsgolint dans le projet analysé ; la session l'a installé dans le scratchpad.

  • oxc-resolver résout comme Node, pas comme TypeScript : il ignore les paquets qui n'ont que des @types et les declare module '*.css', et pourrait faire supprimer un import valide. Oxfmt formate le style à la manière de Prettier, sans les groupes ni l'alignement de TidyJS. Les deux autres n'ont pas de rapport avec le problème. oxc-parser, lui, est le parser de TidyJS depuis le début.

  • L'idée vient de prettier-plugin-organize-imports, dont le service ne contient que le fichier traité (getScriptFileNames: () => [path]). Sur 1 963 fichiers Yeap, elle donne les mêmes diagnostics « inutilisé » que le programme complet, code et position compris, en 6,3 s (3,2 ms par fichier) contre 24,7 s. Elle est intégrée depuis le 7 octobre comme premier étage du repli, et non à la place de l'oracle : quand tous les modules se résolvent mais qu'un cas douteux empêche l'oracle de trancher, TypeScript vérifie le fichier seul et l'ESLint du projet le lint. Les modules manquants restent à la résolution, car en noResolve TypeScript émettrait un 2307 pour tous les imports. Un fichier passe ainsi de 2,04 s à 0,73 s.

  • Cinq correctifs intégrés le 7 octobre, aucun ne change le résultat. Le cache des tsconfig repose sur ts.matchFiles, une fonction interne de TypeScript : s'il disparaît, le cache se désactive. Le transfert brut est limité à la CLI (enableRawTransfer dans src/cli/main.ts) ; l'extension garde le JSON, car le sandbox V8 d'Electron n'a pas été vérifié. Deux idées ont été écartées : remplacer aussi le parse TypeScript de l'oracle par l'AST oxc (coût égal, et les modes ESM/CJS sont internes à TypeScript), et décider qu'un module manque sans programme (2307 ou un autre code selon module et moduleResolution).

  • Il donne les mêmes résultats no-unused-vars que l'ESLint du projet sur 1 964 fichiers, sondes comprises. Les 5 écarts bruts venaient d'un eslint-disable visant une règle non chargée. Coût : 2,4 ms par fichier, plus 0,35 s de chargement. Il faut connaître les options exactes de la règle et savoir si elle est active pour chaque fichier. Ces informations sont dans eslint.config.js, du code avec plugins, et le seul moyen exact de les lire est de charger la config (0,7 s). Pour la mesure, elles ont été recopiées à la main.

  • Refus catégorique le 7 octobre 2026 : cette piste ne sera pas étudiée.

  • Recherche web faite en fin de session (prettier-plugin-organize-imports, PR TypeScript #50931, issue VS Code #148790, TSSLint, @ttsc/lint). Aucun outil ne reproduit l'union TypeScript + ESLint que lit l'extension : chacun applique sa propre règle.

Retenus : 7. Écartés ou refusés : 7, plus une recherche sans résultat. Mesurés sans intégration : 3. TS 7 est intégré en option, mais reste litigieux.

06

Il reste des contournements utilisables tout de suite, et trois décisions à prendre.

La session du 6 octobre s'était arrêtée sur une proposition non tranchée, avec deux points : remplacer les règles de l'oracle par TypeScript sur le fichier seul et ESLint réduit, et passer la copie TypeScript de la CLI en 6.x.
