TidyJS ne retouche pas les imports : il les reconstruit depuis l’AST, puis vérifie que le résultat se reparse.

Ce document décrit le fonctionnement de l’extension VS Code Asmir.tidyjs telle qu’elle existe sur la branche main du dépôt tidyjs (version 1.9.2). Dans Yeap-UI-Apps, elle est le formatter par défaut des fichiers TS, TSX, JS et JSX avec editor.formatOnSave : chaque sauvegarde traverse le moteur décrit ici.

Il couvre le moteur de formatage des imports, ses dépendances, la résolution de configuration et les garde-fous. Il ne détaille ni la commande Sort Selection, ni l’organisation des re-exports, ni le prototype de CLI en cours sur une autre branche.

Le fil : une config est résolue (03), le parser découpe et range chaque import (04), l’IR imprime un bloc neuf aligné (05), et chaque étape peut renoncer plutôt que casser le fichier (06).

01

Le moteur ne dépend que d’un parser natif ; le reste vient de VS Code.

Le package.json ne déclare qu’une dépendance d’exécution : oxc-parser, un parser JavaScript et TypeScript écrit en Rust. esbuild bundle l’extension en ESM dans dist/extension.js et copie à côté le binding natif parser.<plateforme>.node. L’extension installée en contient un seul, celui de la machine qui a construit le .vsix.

Tout le reste est emprunté à l’hôte : les diagnostics TypeScript et ESLint déjà publiés dans VS Code pour savoir quoi supprimer, les paths du tsconfig.json pour réécrire les chemins. Sans ces sources, les options correspondantes ne font simplement rien.

02

Éditeur et dossier partagent le même cœur, pas les mêmes entrées.

Dans l’éditeur, TidyJSFormattingProvider (src/extension.ts:58) est appelé par VS Code à la sauvegarde ou par la commande TidyJS: Format Imports. Il produit un seul TextEdit couvrant la plus petite zone qui diffère, pour ne pas déplacer le curseur ni polluer l’historique d’annulation.

La commande TidyJS: Format Folder (src/batch-formatter.ts) parcourt un dossier et écrit directement sur disque. Elle ignore node_modules, .git, dist, build, out, .next, coverage, .cache et .turbo. Elle ne lit aucun diagnostic : les options de suppression n’y ont pas d’effet.

Si le document a changé entre la lecture et la fin du calcul (version ou texte), l’édition est abandonnée et une relance est programmée 150 ms plus tard, au plus une fois toutes les 2 s par document.

03

La configuration se résout par fichier, et un seul fichier de config gagne.

ConfigLoader remonte depuis le dossier du document jusqu’à la racine du workspace et s’arrête au premier .tidyjsrc ou tidyjs.json trouvé, le premier l’emportant à égalité de dossier. Les fichiers parents ne sont pas fusionnés automatiquement : il faut un extends. C’est ce que fait Yeap-UI-Apps : apps/paye/tidyjs.json étend ../../tidyjs.json.

La fusion part de DEFAULT_CONFIG et applique les sources du plus général au plus spécifique. format, importOrder et pathResolution sont fusionnés clé par clé ; groups et excludedFolders sont remplacés en bloc. computeAutoOrder donne ensuite un ordre unique à chaque groupe : un doublon est poussé au créneau libre suivant. Un ordre absent vaut 999 dans un fichier de config (ConfigLoader le fixe avant la résolution, d’où 999 → 1013 pour quinze groupes sans order) et prend le premier créneau libre à partir de 0 dans les réglages VS Code.

Le résultat est mis en cache par document et invalidé quand un fichier de config change ou quand un réglage tidyjs.* est modifié. Le parser n’est recréé que si la config sérialisée diffère de la précédente ; cette sérialisation est un JSON.stringify qui réduit chaque match à {}, donc modifier seulement une regex dans un fichier de config ne recrée pas le parser, alors qu’un changement de réglage tidyjs.* force la recréation. Le réglage debug n’est jamais lu depuis un fichier.

04

Le parser transforme chaque déclaration en unités typées, rangées dans un groupe.

ImportParser.parse (src/parser.ts) appelle oxc une fois. Une erreur de syntaxe n’est pas corrigée : elle remonte en invalidImports et le fichier reste intact. Seul compte le bloc d’imports contigu en tête de fichier, après d’éventuelles directives comme 'use client' (getLeadingImportBlockEnd, ligne 239) : un import placé après du code n’est jamais déplacé.

Chaque déclaration est éclatée : import React, { useState, type FC } from 'react' devient trois unités, default, named et typeNamed. Les unités sont filtrées si des diagnostics le demandent, fusionnées par source (consolidateImportsBySource, ligne 518), puis placées dans leur groupe et triées (organizeImportsIntoGroups, ligne 642). Cliquer un champ pour voir la décision qu’il porte.

Le tri dans un groupe suit importOrder (sideEffect 0, default 1, named 2, typeOnly 3), puis le sortOrder du groupe s’il existe (motifs avec *), sinon l’ordre alphabétique de la source.

Une unité par nature d’import

Le parser éclate chaque déclaration : default, named, typeDefault, typeNamed, sideEffect. Un namespace (* as X) est rangé en default, un namespace typé en typeDefault. C’est ce découpage qui permet de trier par nature à l’intérieur d’un groupe.

Au lieu deGarder la déclaration telle qu’écrite : impossible alors de placer les types en fin de groupe sans réécrire les specifiers.

05

L’alignement des from est calculé avant d’écrire la moindre ligne.

Les groupes triés par order passent dans buildDocument (src/ir/builders.ts), qui produit une représentation intermédiaire : du texte, des sauts de ligne, et des ancres d’alignement qui séparent ce qui précède from de ce qui suit. Chaque groupe reçoit un commentaire // Nom du groupe et ses ancres partagent un identifiant.

printDocument (src/ir/printer.ts) travaille en deux passes. La mesure retient, par groupe, la largeur maximale avant from ; pour un import multiligne, c’est l’indentation plus le specifier le plus long plus la virgule. Le rendu complète ensuite chaque ligne par des espaces jusqu’à cette colonne. Un import nommé passe en multiligne dès qu’il a plus d’un specifier, sauf si maxLineWidth est défini ; les specifiers sont triés par longueur par défaut.

Le bloc produit remplace des lignes entières, du premier au dernier import, en englobant les commentaires // juste au-dessus et les commentaires orphelins qui suivent après une ligne vide. Un bloc /* */ d’en-tête de fichier est préservé.

06

À chaque doute, le moteur renonce plutôt que d’écrire.

Le résultat final, tris et re-exports compris, est reparsé par oxc avant d’être appliqué (validateFormattedOutput). S’il ne se parse plus, rien n’est écrit et l’éditeur affiche TidyJS formatting aborted. Les autres garde-fous agissent plus tôt et sans bruit.

Limite : bloc de tête seulement
Un import situé après une instruction n’est ni trié ni regroupé. Le déplacer imposerait de déplacer le code intermédiaire, ce que le remplacement par plage ne sait pas faire sans risque.
Limite : commentaires d’imports
Les commentaires // du bloc sont remplacés par les commentaires de groupe générés. Un commentaire écrit à la main entre deux imports est perdu.
Prérequis des suppressions
removeUnusedImports et removeMissingModules lisent les diagnostics déjà publiés au moment du formatage (cache de 100 ms). Si le serveur TypeScript ou ESLint n’a pas fini son analyse, rien n’est retiré à cette sauvegarde.
Écart constaté : sortTypeMembers
Dans l’éditeur, quand le fichier contient des imports, le post-traitement ne se lance que si sortEnumMembers, sortExports ou sortClassProperties est actif (src/extension.ts:311 sur main). sortTypeMembers seul n’est donc pas appliqué, alors que le mode dossier l’applique. Yeap-UI-Apps active les quatre options ensemble, ce qui masque l’écart.
Point de surveillance : binding natif
Le .vsix embarque le binding oxc de la plateforme qui l’a construit. Un poste sur une autre architecture doit recevoir un build correspondant.
